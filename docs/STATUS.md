# گزارش وضعیت سامانه بنکداری هوشمند — نسخه فعلی

> تاریخ به‌روزرسانی: ۱۴۰۵/۰۹/۰۵ (۲۰۲۶-۱۱-۲۶)
> این سند گزارش صادقانه درصد تکمیل ماژول‌ها، نتایج واقعی تست‌ها و نقشه راه ادامه است.

## ۱) معماری پیاده‌سازی‌شده

- **Frontend:** Next.js 16 (App Router) + TypeScript + Tailwind CSS 4 + shadcn/ui + Recharts — تک‌صفحه‌ای (SPA) در مسیر `/` با ناوبری hash؛ فارسی، RTL کامل، فونت Vazirmatn، تاریخ شمسی با `Intl`، اعداد فارسی، مبالغ با تبدیل ریال→تومان در UI.
- **Backend:** Route Handlers زیر `/api/*` با قالب پاسخ یکپارچه `{ ok, data }` / `{ ok, error:{code,message} }`، اعتبارسنجی Zod، Rate Limiting مقدماتی در حافظه، Audit Log روی عملیات حساس.
- **Database:** PostgreSQL 16 + Prisma (لوکال با اسکریپت pg-local، ابر با Render Blueprint یا Supabase/Neon). مبالغ مالی به‌صورت **Integer ریال**؛ مقادیر انبار **Integer واحد پایه**. مهاجرت SQLite → PostgreSQL کامل و اجرا شده است (مستند در `docs/postgres-migration.md`).
- **حساب‌ها و دسترسی‌ها:** احراز هویت با شماره موبایل + رمز (scrypt + salt)، نشست با توکن تصادفی و Hash SHA-256 در DB، کوکی HttpOnly، لغو نشست هنگام غیرفعال‌سازی/تغییر رمز، RBAC کامل با ۱۰ نقش و ۲۹ مجوز — کنترل در **سرور**، نه فقط UI.
- **موتور موجودی:** رزرو اتمیک با `UPDATE` شرطی داخل `Transaction` (ضد Overselling)، آزادسازی کنترل‌شده، خروج فیزیکی با **FEFO**، ورود کالا با لات/بچ/انقضا، تعدیل با دلیل، Ledger کامل حرکات.
- **ماشین حالت سفارش:** `SUBMITTED → RESERVED → CONFIRMED → CREDIT_APPROVED/PAID → PICKING → READY_FOR_DISPATCH → DISPATCHED → DELIVERED → COMPLETED` + مسیرهای `REJECTED`/`CANCELLED` با آزادسازی رزرو و سند اصلاحی مالی.
- **موتور قیمت‌گذاری:** سمت سرور؛ اولویت `CUSTOMER > GROUP > TERRITORY > VOLUME > DEFAULT`؛ پنجره زمانی و محدوده مقدار؛ خطای صریح `AMBIGUOUS_PRICE_RULES` در تساوی ناسازگار؛ Snapshot کامل قیمت در `OrderItem` تا تغییر قیمت آتی، فاکتورهای گذشته را تغییر ندهد.
- **مالی:** دفتر مشتری و تأمین‌کننده (Ledger-based)، فاکتور در لحظه تحویل، دریافت/پرداخت با سند منفی، سند اعتبار (CREDIT_NOTE) مرجوعی، عدم حذف مخرب اسناد.
- **Idempotency:** کلید یکتا در ثبت سفارش — ارسال مجدد در قطع اینترنت، سفارش تکراری نمی‌سازد (تست شده).
- **اعلان‌ها:** رویدادمحور در DB (سفارش جدید، وضعیت، کم‌موجودی، مرجوعی، پیام) + Polling سبک در UI.
- **پیام‌رسانی:** گفت‌وگوی خصوصی ذخیره‌شده در DB با اعلان؛ نسخه اول با Polling.
- **استقرار:** `output: standalone` + `render.yaml` (وب‌سرویس + PostgreSQL رایگان در ریجن فرانکفورت) — `docs/render-deploy.md`؛ معادل VPS/Docker نیز مستند است (`راهنمای-نصب-و-راه-اندازی.md` بخش ۵).
- **CI:** GitHub Actions (`.github/workflows/ci.yml`) — typecheck، lint، تست با PostgreSQL موقت و build روی هر push/PR به main؛ خطاهای TypeScript پنهان نمی‌شوند (`ignoreBuildErrors` حذف شده).

## ۳) نتایج واقعی تست‌ها

- **تست‌های واحد (node:test — بدون دیتابیس):** ۳۳/۳۳ PASS — crypto، exporters/importers (CSV/XLSX/JSON/TS)، الگوهای تلگرام و اسکجولر بکاپ، پارس AI، سلامت بکاپ. در CI روی هر push اجرا می‌شود.
- **تست‌های یکپارچه (با PostgreSQL):** ۶/۶ PASS — لایه AI (پیکربندی/snapshot) و جریان حیاتی سفارش ویزیتور (ثبت مشتری → سفارش → Idempotency → scoping → مشاهده مدیر). در CI با PostgreSQL موقت اجرا می‌شود.
- **تست دود کامل (scripts/smoke.sh):** ۶۵/۶۵ PASS روی سرور standalone با seed تازه — سناریوهای حیاتی زیر + جریان فروشگاه ویزیتور، WebP و گرادیانت موبایل.

**سناریوهای حیاتی سند پروژه:**
- ✅ سناریو ۱ (ضد Overselling): دو سفارش هم‌زمان از موجودی محدود → دقیقاً یکی رزرو قطعی می‌شود، دیگری `INSUFFICIENT_STOCK 409`
- ✅ سناریو ۲ (رزرو ≠ خروج فیزیکی): ثبت سفارش فقط Reserved را کم می‌کند؛ Physical تنها در `deliver` با FEFO کاهش یافت (۱۰۰ → ۵۲ پایه)
- ✅ سناریو ۳ (درخواست تکراری): ارسال مجدد با همان Idempotency Key → `idempotent:true`، سفارش تکراری ساخته نشد
- ✅ سناریو ۴ (لغو): لغو سفارش → رزرو آزاد شد و Available به ۱۰۰ بازگشت
- ✅ سناریو ۵ (قیمت اختصاصی): قیمت CUSTOMER مشتری کاوه (۲٬۱۰۰٬۰۰۰) بر DEFAULT (۲٬۲۰۰٬۰۰۰) مقدم بود
- ✅ سناریو ۶ (انقضا): لات‌های منقضی در UI و API تفکیک و از مسیر عادی فروش خارج‌اند (FEFO اولویت بچ زودترمنقضی)
- ✅ سناریو ۷ (مرجوعی): درخواست روی سفارش تحویل‌شده، QC با RESTOCK → ورود ۲۴ پایه به انبار + سند اعتبار در Ledger
- ✅ سناریو ۸ (دسترسی): ویزیتور به `/api/finance` و `/api/users` دسترسی ندارد (403) اما می‌تواند سفارش ثبت کند
- ✅ سقف اعتبار: سفارش اعتباری مازاد بر سقف → `CREDIT_EXCEEDED 402`
- ✅ ورود اشتباه → `BAD_CREDENTIALS 401` + ثبت Audit با نتیجه DENIED

**راستی‌آزمایی مرورگر (Agent Browser):** ورود مدیر، داشبورد با داده واقعی، لیست/جزئیات سفارش با Timeline، ثبت سفارش کامل از UI با پیش‌نمایش قیمت زنده سرور، انبار (موجودی/لات‌ها/گردش)، گزارش‌ها، کاربران/ماتریس دسترسی، اپ ویزیتور موبایل با کارنامه — بدون خطای کنسول؛ چیدمان RTL/فونت/اعداد فارسی در دسکتاپ و موبایل تأیید شد.

## ۴) محدودیت‌های شناخته‌شده (صادقانه)

1. **Runtime:** استقرار واقعی روی Render/PaaS به‌صورت بلوپرینت مستند و آماده است (`render.yaml` + `docs/render-deploy.md`)؛ روی هاست‌های خواب‌شونده اسکجولر داخلی بکاپ متوقف می‌شود — راهکار cron بیرونی در `docs/integrations.md` مستند است.
2. **اعتبارنامه‌های واقعی یکپارچه‌سازی‌ها:** کد آماده است؛ OAuth گوگل، سرویس‌اکانت، توکن تلگرام و کلید AI باید توسط مالک پروژه واقعاً تنظیم و تأیید شوند.
3. **پرداخت آنلاین و SMS:** Adapter طراحی شده ولی اتصال واقعی به درگاه/سرویس پیامک ایرانی نیازمند اعتبارنامه‌های واقعی است.
4. **پیام‌رسانی Real-time:** فعلاً Polling؛ ارتقای WebSocket در فاز بعد.
5. **دسترسی خروجی از ایران:** سرویس‌های گوگل/تلگرام/OpenRouter به پروکسی خروجی نیاز دارند — پشتیبانی در کد (متغیرهای proxy) و مستندات کامل است؛ برقراری یک پروکسی واقعی با مالک پروژه است.
6. **نقشه تعاملی مناطق:** Leaflet هنوز اضافه نشده؛ داده GIS فقط از ورود رسمی مدیر پذیرفته می‌شود (بدون حدس).
7. **E2E با Playwright:** سناریوهای E2E فعلاً به‌صورت دستی اجرا شد؛ خودکارسازی Playwright در فاز QA.
8. **حذف داده DEMO:** کاتالوگ/قیمت‌ها/موجودی اولیه با پرچم `isDemo` (DEMO_SEED) هستند و مدیر می‌تواند اصلاح/غیرفعال کند.

## ۵) نقشه راه ادامه (بازنویسی فازها بر اساس وضعیت فعلی)

- **فاز A — استقرار واقعی روی Render:** Apply بلوپرینت `render.yaml`، تنظیم `ADMIN_PASSWORD`/`DEMO_USERS_PASSWORD`/`INTEGRATION_SECRET_KEY`، اجرای Seed و تأیید سلامت سرویس + دیتابیس.
- **فاز B — راه‌اندازی واقعی یکپارچه‌سازی‌ها:** OAuth Client گوگل، Service Account، اشتراک‌گذاری پوشه/شیت، توکن تلگرام، کلید AI و تأیید چک‌لیست نهایی (`docs/integrations.md`).
- **فاز C — خرید و تأمین:** درخواست/سفارش خرید رسمی، فاکتور خرید، هزینه‌های جانبی، سند مالی خرید، بهای تمام‌شده واقعی لات از فاکتور خرید.
- **فاز D — PWA ویزیتور:** صف آفلاین سفارش با همگام‌سازی و تأیید سرور.
- **فاز E — پورسانت کامل:** قوانین درصدی/وصولی/پلکانی با Snapshot و رویداد معکوس هنگام مرجوعی.
- **فاز F — نقشه Leaflet:** ترسیم Polygon مدیر، اعتبارسنجی هم‌پوشانی، نسخه‌بندی مناطق.
- **فاز G — حسابداری رسمی:** دفاتر روزنامه/کل، دوره مالی، تراز آزمایشی.
- **فاز H — QA خودکار:** Playwright E2E + تست‌های هم‌زمانی، Security Review نهایی.

## ۶) راهنمای اجرای محلی و استقرار

**اجراهای پرکاربرد:**
```bash
npm run dev                 # سرور توسعه (پورت 3000)
npm run typecheck           # بررسی تایپ (بدون خطا = قابل build)
npm run lint                # ESLint
npm test                    # تست‌های node:test (با PostgreSQL در دسترس)
npm run db:push             # اعمال اسکیما
npm run db:seed             # Seed اولیه Idempotent (رمزها از .env)
bash scripts/start-env.sh   # راه‌اندازی PostgreSQL محلی + سرور توسعه
bash scripts/smoke.sh       # تست دود کامل — ۳۶ چک (نیازمند سرور در حال اجرا)
```

**حساب‌های نمایشی این محیط:** مدیر `09120000000 / Admin#1404` — ویزیتور `09120000005 / Demo#1404` — سایر نقش‌ها `09120000001..9 / Demo#1404`. در Production این رمزها **باید** تغییر کنند (متغیرهای `ADMIN_PASSWORD` و `DEMO_USERS_PASSWORD`).

**چک‌لیست استقرار Render (فاز A):**
1. Apply بلوپرینت `render.yaml` (وب‌سرویس + PostgreSQL رایگان در فرانکفورت) — `docs/render-deploy.md`.
2. Environment: `ADMIN_PASSWORD`، `DEMO_USERS_PASSWORD`، `INTEGRATION_SECRET_KEY` (و در صورت نیاز متغیرهای پروکسی خروجی).
3. پس از اولین دیپلوی، یک بار Seed اجرا شود و ورود مدیر تأیید شود.
4. اگر سرویس می‌خوابد: cron بیرونی به `/api/integrations/scheduler/tick` با هدر `x-cron-secret` — چک‌لیست در `docs/integrations.md`.
5. Health Check `/api` و مانیتورینگ لاگ‌های Render.
